# Deviations from the prompt

Every place the scaffold differs from `SAAS_TEMPLATE_PROMPT.md`, and why. Nothing is dropped silently.

| # | Area | What the prompt says | What the scaffold does | Why |
|---|---|---|---|---|
| 1 | Catalog ownership (4.1) | The catalog database is "owned by the Tenancy module". | The **tenant directory** part of the catalog (tenants, placement, modules, plans, entitlements, migration state) is defined in `Core.Catalog` (`CatalogDbContext`, schema `catalog`). Tenancy and Identity keep their own catalog data in their own schemas (`tenancy`, `identity`). Only Core, Tenancy, Identity and the Migrator may write the directory. | Every host must resolve tenants from the catalog, and modules may not reference each other (2.2). Putting the directory in Core gives one mapping of those tables, instead of a second, duplicated mapping per host, which would break the single-source rule. |
| 2 | `platform.yaml` shape (2.1) | Services have `key`, `port`, `owns`. | Services may also declare `databases: [tenant, catalog]` (default `[tenant]`). | The Migrator's list of DbContexts and the per-provider migrations projects are generated from `platform.yaml`; the generator needs to know which databases each service uses. |
| 3 | Suspended tenants (4.1, lifecycle) | `ITenantConnectionResolver` "refuses tenants that are suspended or deleted"; suspended tenants "can sign in and read but not write". | The resolver allows suspended tenants for reads and refuses them for writes; every write through a module DbContext is also refused by the audit interceptor (`platform.tenant-read-only`). Provisioning, pending-deletion and deleted tenants are refused (the Migrator and onboarding use a separate maintenance path that allows provisioning). | The two statements conflict; this honours the lifecycle rule and still guarantees no writes. |
| 4 | Product name in source (0) | Parameters are written once into `platform.yaml`; nothing else may repeat them. | Assembly names, root namespaces, package metadata, audiences, volume names and every generated file come from `platform.yaml`. C# `namespace` declarations in hand-written code still start with `Acme`. | C# has no way to take a namespace from configuration. Renaming the product is a one-time, scripted codemod (planned with `scripts/new-module` in milestone 6), not an ongoing source of drift: the build fails if `platform.yaml` and the code disagree, because generated code uses the new namespace. |
| 5 | Document numbering on PostgreSQL (4.2, 4.13) | `UPDATE … RETURNING` on PostgreSQL. | `INSERT … ON CONFLICT DO UPDATE … RETURNING`: one atomic statement that also creates the counter on first use. SQL Server uses `UPDATE … OUTPUT`, creating the row under `UPDLOCK, HOLDLOCK` on first use. Both are tested for duplicates under concurrency. | Avoids a separate insert path and race on PostgreSQL; same guarantees. |
| 6 | Database tracing (4.11) | OpenTelemetry for EF Core. | Npgsql's built-in `ActivitySource` is traced. SQL Server and EF Core command spans are not yet included. | The OpenTelemetry EF Core and SqlClient instrumentation packages are still prerelease. To be revisited when they ship stable. |
| 7 | Banned APIs (4.3) | Ban `DateTime.Now`, `DateTime.Today`, `DateTimeOffset.Now`. | `DateTime.UtcNow` and `DateTimeOffset.UtcNow` are banned as well. | The prompt also says "never call the static clock"; `TimeProvider` is the only clock. Stricter, not looser. |
| 8 | Compose variables (8) | `deploy/.env.example` lists configuration keys with no values. | `deploy/.env.example` is generated from the configuration schema (application settings). A second file, `deploy/compose.env.example`, lists the variables the published compose file needs (image names, passwords), also generated, also without values. | They are different facts: one is the application's configuration schema, the other is what `aspire publish` asks for. Mixing them would make the schema check (13.3) impossible. |
| 9 | AppHost settings (2.1) | No per-environment settings files holding values. | `backend/src/AppHost/appsettings.json` holds the two local-development choices: `Database:Provider` and `Tenancy:BaseDomain`. | The AppHost only runs on developer machines; these are the documented "one configuration value" switches (8). No service host has a settings file with values, and an architecture test fails on any `appsettings.*.json`. |
| 10 | SQL Server retries | — | `EnableRetryOnFailure` is not turned on for SQL Server. | EF Core's retrying execution strategy rejects user-initiated transactions, which the outbox and numbering rely on. Transient faults are handled at the HTTP resilience layer and by message retries. To be revisited per deployment (Azure SQL). |
| 11 | Machine sign-in (4.4) | `client_credentials` with `private_key_jwt` (RFC 7523). | Same, but the client assertion's JWT header must be `typ: client-authentication+jwt`. | OpenIddict 7 requires that `typ` for client assertions. Machine agents (and the enrollment docs) must set it. |
| 12 | Token claims (4.5) | The `roles` claim is an array. | A principal with exactly one role gets the claim as a single string; two or more get an array. | OpenIddict serialises a single-valued claim as a string. Services read both forms (`FindAll`), and a test covers it. |
| 13 | Token validation (4.4) | Check `iss`, `exp` and `nbf`. | Access tokens carry `iat` and `exp` but no `nbf` (OpenIddict doesn't emit it). Validation checks `iss`, `aud`, `exp`, `typ`, the ES256 signature and the key's `kid`; `nbf` is checked when present. | A missing claim can't be validated. |
| 14 | Support-access tokens (4.4) | Operators get a token with the tenant's `tenant_id`, restricted `roles` and an `act` claim. | Identity signs those tokens itself with the token server's ES256 key (`SupportTokenIssuer`), instead of through an OpenIddict endpoint flow. Tokens last 10 minutes and are for the one service that owns the granted module. | OpenIddict's token exchange needs a subject token it issued, and operators aren't users of any tenant. No custom *grant* is added; the token has the same format and is validated like any other. |
| 15 | Platform operators (4.4) | A separate realm with passkey or TOTP MFA, signing in to its own console client on its own hostname. | A separate realm in the catalog (`Tenancy` schema). Sign-in is password plus TOTP (always required), answered by a Data Protection time-limited session token with its own `Operator` authentication scheme. Passkeys for operators and a separate OIDC client are not implemented. | The operator console is out of scope for the template; the realm, MFA, lockout, support-access approval and audit are. Add passkeys and an OIDC client when the console is built. |
| 16 | Passkeys (4.4) | Passkeys (WebAuthn) preferred for users. | Registration and sign-in endpoints use ASP.NET Core Identity 10's passkey APIs, with a small script served from the sign-in host. They are not covered by automated tests, because that needs a WebAuthn authenticator. | Verify manually in a browser; add a virtual-authenticator Playwright test in milestone 4. |
| 17 | SignalR under the BFF (4.4) | The Gateway closes connections when the session ends. | WebSocket connections are proxied with the session's token and re-authenticated on every reconnect, but an already-open connection is not force-closed when the session ends. | YARP gives no handle on open tunnels. Connections are short-lived behind the access-token lifetime and the Notification hub rechecks `access_version`. |
| 18 | Token exchange (4.4) | RFC 8693 through OpenIddict's built-in flow. | Built-in flow, with OpenIddict's `ValidateAuthorizedParty` handler replaced by `ExchangeAuthorizedParty`: tokens may be presented by one of our platform services during an exchange; authorization codes and refresh tokens keep the strict "only the client it was issued to" rule. | The built-in rule makes service-to-service exchange impossible. The endpoint itself only accepts platform service clients. |
| 19 | Transport security (4.12) | TLS everywhere outside a developer's machine. | The token server's `RequireTransportSecurity` option (default on) is turned off by the AppHost and the published compose file, because services reach Identity over plain HTTP on the private network and the Gateway terminates TLS. | Only the Gateway is public; internal TLS (mesh or mTLS) is a platform concern, listed in the runbooks. |
| 20 | DPoP (4.4, optional) | Bind machine tokens to the device key if the OpenIddict version supports it. | Not implemented. | Optional in the prompt; machine tokens are 15 minutes and signed requests aren't required yet. Revisit when OpenIddict's server DPoP support is confirmed stable. |
| 21 | Platform service tokens (4.4, 4.5) | A module's service token is only for background or system work. | A platform service's own token has `tenant:any` and `admin` in the modules **it owns** only. Cross-module calls on behalf of a user use the exchanged user token instead. | Least privilege: no service token is admin everywhere. |
| 22 | Suspended tenants (4.1) | Suspended tenants can read but not write. | Writes by the tenant's own principals are refused (`platform.tenant-read-only`). Platform maintenance by platform service principals (revoking tokens, offboarding) is allowed. | Offboarding must revoke tokens and audit while the tenant is suspended. |
| 23 | Onboarding order (5) | Create the database, migrate, seed, create the first admin invitation, enable the plan's modules. | Catalog row → database → migrations → reference data → modules → **activate** → callback URIs → first-admin invitation. The reference-data step is a placeholder (modules create their own reference data on first use). | Services refuse a tenant that is still Provisioning, so it is activated before the steps that call Identity. A failed step resumes where it stopped. |
| 24 | Offboarding export (5) | Deletion first produces a full data export. | The lifecycle, grace period, token revocation, callback removal and database deletion are implemented. The per-module export (`ITenantExporter`) is a no-op until milestone 3 adds file storage. | There is no module data or `IFileStorage` yet. |
| 25 | Response mode (4.4) | Authorization code + PKCE through the Gateway. | The Gateway uses `response_mode=query` (a GET callback). | The default `form_post` would need `SameSite=None` cookies, which conflicts with the required `SameSite=Lax` session cookie. |
