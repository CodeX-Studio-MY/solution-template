# Deviations from the prompt

Every place the scaffold differs from `SAAS_TEMPLATE_PROMPT.md`, and why. Nothing is dropped silently.

| # | Area | What the prompt says | What the scaffold does | Why |
|---|---|---|---|---|
| 1 | Catalog ownership (4.1) | The catalog database is "owned by the Tenancy module". | The **tenant directory** part of the catalog (tenants, placement, modules, plans, entitlements, migration state) is defined in `Core.Catalog` (`CatalogDbContext`, schema `catalog`). Tenancy and Identity keep their own catalog data in their own schemas (`tenancy`, `identity`). Only Core, Tenancy, Identity and the Migrator may write the directory. | Every host must resolve tenants from the catalog, and modules may not reference each other (2.2). Putting the directory in Core gives one mapping of those tables, instead of a second, duplicated mapping per host, which would break the single-source rule. |
| 2 | `platform.yaml` shape (2.1) | Services have `key`, `port`, `owns`. | Services may also declare `databases: [tenant, catalog]` (default `[tenant]`). | The Migrator's list of DbContexts and the per-provider migrations projects are generated from `platform.yaml`; the generator needs to know which databases each service uses. |
| 3 | Suspended tenants (4.1, lifecycle) | `ITenantConnectionResolver` "refuses tenants that are suspended or deleted"; suspended tenants "can sign in and read but not write". | The resolver allows suspended tenants for reads and refuses them for writes; every write through a module DbContext is also refused by the audit interceptor (`platform.tenant-read-only`). Provisioning, pending-deletion and deleted tenants are refused (the Migrator and onboarding use a separate maintenance path that allows provisioning). | The two statements conflict; this honours the lifecycle rule and still guarantees no writes. |
| 4 | Product name in source (0) | Parameters are written once into `platform.yaml`; nothing else may repeat them. | Assembly names, root namespaces, package metadata, audiences, volume names and every generated file come from `platform.yaml`. C# `namespace` declarations in hand-written code still start with `Acme`. | C# has no way to take a namespace from configuration. Renaming the product is a one-time, scripted codemod (planned with `scripts/new-module` in milestone 6), not an ongoing source of drift: the build fails if `platform.yaml` and the code disagree, because generated code uses the new namespace. |
| 5 | Document numbering on PostgreSQL (4.2, 4.13) | `UPDATE … RETURNING` on PostgreSQL. | `INSERT … ON CONFLICT DO UPDATE … RETURNING`: one atomic statement that also creates the counter on first use. SQL Server uses `UPDATE … OUTPUT`, creating the row under `UPDLOCK, HOLDLOCK` on first use. Both are tested for duplicates under concurrency. | Avoids a separate insert path and race on PostgreSQL; same guarantees. |
| 6 | Database tracing (4.11) | OpenTelemetry for EF Core. | Npgsql's built-in `ActivitySource` is traced. SQL Server and EF Core command spans are not yet included. | The OpenTelemetry EF Core and SqlClient instrumentation packages are still prerelease. To be revisited when they ship stable. |
| 7 | Banned APIs (4.3) | Ban `DateTime.Now`, `DateTime.Today`, `DateTimeOffset.Now`. | `DateTime.UtcNow` and `DateTimeOffset.UtcNow` are banned as well. | The prompt also says "never call the static clock"; `TimeProvider` is the only clock. Stricter, not looser. |
| 8 | Compose variables (8) | `deploy/.env.example` lists configuration keys with no values. | `deploy/.env.example` is generated from the configuration schema (application settings). A second file, `deploy/compose.env.example`, lists the variables the published compose file needs (image names, passwords), also generated, also without values. | They are different facts: one is the application's configuration schema, the other is what `aspire publish` asks for. Mixing them would make the schema check (13.3) impossible. |
| 9 | AppHost settings (2.1) | No per-environment settings files holding values. | `backend/src/AppHost/appsettings.json` holds the two local-development choices: `Database:Provider` and `Tenancy:BaseDomain`. | The AppHost only runs on developer machines; these are the documented "one configuration value" switches (8). No service host has a settings file with values, and an architecture test fails on any `appsettings.*.json`. |
| 10 | SQL Server retries | — | `EnableRetryOnFailure` is not turned on for SQL Server. | EF Core's retrying execution strategy rejects user-initiated transactions, which the outbox and numbering rely on. Transient faults are handled at the HTTP resilience layer and by message retries. To be revisited per deployment (Azure SQL). |
| 11 | Machine sign-in (4.4) | `client_credentials` with `private_key_jwt` (RFC 7523). | Same, but the client assertion's JWT header must be `typ: client-authentication+jwt`. | OpenIddict 7 requires that `typ` for client assertions. Machine agents (and the enrollment docs) must set it. |
| 12 | Token claims (4.5) | The `roles` claim is an array. | A principal with exactly one role gets the claim as a single string; two or more get an array. | OpenIddict serialises a single-valued claim as a string. Services read both forms (`FindAll`), and a test covers it. |
| 13 | Token validation (4.4) | Check `iss`, `exp` and `nbf`. | Access tokens carry `iat` and `exp` but no `nbf` (OpenIddict doesn't emit it). Validation checks `iss`, `aud`, `exp`, `typ`, the ES256 signature and the key's `kid`; `nbf` is checked when present. | A missing claim can't be validated. |
| 14 | Support-access tokens (4.4) | Operators get a token with the tenant's `tenant_id`, restricted `roles` and an `act` claim. | Identity signs those tokens itself with the token server's ES256 key (`SupportTokenIssuer`), instead of through an OpenIddict endpoint flow. Tokens last 10 minutes and are for the one service that owns the granted module. | OpenIddict's token exchange needs a subject token it issued, and operators aren't users of any tenant. No custom *grant* is added; the token has the same format and is validated like any other. |
| 15 | Platform operators (4.4) | A separate realm with passkey or TOTP MFA, signing in to its own console client on its own hostname. | A separate realm in the catalog (`Tenancy` schema). Sign-in is password plus TOTP (always required), answered by a Data Protection time-limited session token with its own `Operator` authentication scheme. Passkeys for operators and a separate OIDC client are not implemented. | The operator console is out of scope for the template; the realm, MFA, lockout, support-access approval and audit are. Add passkeys and an OIDC client when the console is built. |
| 16 | Passkeys (4.4) | Passkeys (WebAuthn) preferred for users. | Registration and sign-in endpoints use ASP.NET Core Identity 10's passkey APIs, with a small script served from the sign-in host. They are not covered by automated tests, because that needs a WebAuthn authenticator. | Verify manually in a browser; add a virtual-authenticator Playwright test in milestone 4. |
| 17 | SignalR under the BFF (4.4) | The Gateway closes connections when the session ends. | WebSocket connections are proxied with the session's token and re-authenticated on every reconnect, but an already-open connection is not force-closed when the session ends. | YARP gives no handle on open tunnels. Connections are short-lived behind the access-token lifetime and the Notification hub rechecks `access_version`. |
| 18 | Token exchange (4.4) | RFC 8693 through OpenIddict's built-in flow. | Built-in flow, with OpenIddict's `ValidateAuthorizedParty` handler replaced by `ExchangeAuthorizedParty`: tokens may be presented by one of our platform services during an exchange; authorization codes and refresh tokens keep the strict "only the client it was issued to" rule. | The built-in rule makes service-to-service exchange impossible. The endpoint itself only accepts platform service clients. |
| 19 | Transport security (4.12) | TLS everywhere outside a developer's machine. | The token server's `RequireTransportSecurity` option (default on) is turned off by the AppHost and the published compose file, because services reach Identity over plain HTTP on the private network and the Gateway terminates TLS. | Only the Gateway is public; internal TLS (mesh or mTLS) is a platform concern, listed in the runbooks. |
| 20 | DPoP (4.4, optional) | Bind machine tokens to the device key if the OpenIddict version supports it. | Not implemented. | Optional in the prompt; machine tokens are 15 minutes and signed requests aren't required yet. Revisit when OpenIddict's server DPoP support is confirmed stable. |
| 21 | Platform service tokens (4.4, 4.5) | A module's service token is only for background or system work. | A platform service's own token has `tenant:any` and `admin` in the modules **it owns** only. Cross-module calls on behalf of a user use the exchanged user token instead. | Least privilege: no service token is admin everywhere. |
| 22 | Suspended tenants (4.1) | Suspended tenants can read but not write. | Writes by the tenant's own principals are refused (`platform.tenant-read-only`). Platform maintenance by platform service principals (revoking tokens, offboarding) is allowed. | Offboarding must revoke tokens and audit while the tenant is suspended. |
| 23 | Onboarding order (5) | Create the database, migrate, seed, create the first admin invitation, enable the plan's modules. | Catalog row → database → migrations → reference data → modules → **activate** → callback URIs → first-admin invitation. The reference-data step is a placeholder (modules create their own reference data on first use). | Services refuse a tenant that is still Provisioning, so it is activated before the steps that call Identity. A failed step resumes where it stopped. |
| 24 | Offboarding export (5) | Deletion first produces a full data export. | The lifecycle, grace period, token revocation, callback removal and database deletion are implemented. The per-module export (`ITenantExporter`) is still a no-op. | File storage now exists (milestone 3), but no module implements an exporter yet; each module's exporter is added with its data in milestone 5. |
| 25 | Response mode (4.4) | Authorization code + PKCE through the Gateway. | The Gateway uses `response_mode=query` (a GET callback). | The default `form_post` would need `SameSite=None` cookies, which conflicts with the required `SameSite=Lax` session cookie. |
| 26 | Malware scanning (4.9) | A scan hook before files become available. | `IMalwareScanner` is called on every upload and its default adapter, `NoScanner`, accepts everything. Uploads are still checked for size, extension and content type (the content is sniffed, not trusted from the header). | A real scanner is a deployment choice (ClamAV, Defender for Storage). Register your own `IMalwareScanner`. |
| 27 | Email failures (6) | Notification sends email. | A failed send is logged and does not fail the event, so the in-app notification is never lost or retried forever because a mail server is down. There is no email retry queue. | A broken SMTP server must not dead-letter business events. Add a retrying sender if email must be guaranteed. |
| 28 | Unrouted events (4.8) | Not specified. | Events nobody has a queue for go to an alternate exchange and a queue of their own instead of being dropped. | Publishing before a consumer has declared its queue (first start) would otherwise lose the event silently. |
| 29 | Dead-letter replay (4.8) | Replay a dead-lettered message. | Replay publishes the message back to the exchange with its original routing key, so every consumer bound to that key receives it again, not only the one that failed. Consumers are idempotent (inbox), so the extra deliveries are skipped. | A queue-to-queue shovel would bypass the routing the rest of the system relies on. |
| 30 | Idempotency keys (4.7) | Idempotency-Key makes create endpoints safe to retry. | A key whose first request never finished (a crash) is treated as abandoned after a time window and can be used again. The stored hash covers the method, path and body. | Without a window, one crash would block a client's retry forever. |
| 31 | Quote at submit (7.1) | A request needs its quote file. | A quote is optional at submit; the file endpoints (upload, replace, download) exist. | The reference scenario's rules are enforced by tenant settings in milestone 5 (a tenant may require a quote); the default stays permissive. |
| 32 | Scheduler publishing (4.8, 4.14) | Jobs publish through the outbox. | The Scheduler has no module database, so it sends the reminder trigger straight to the broker with publisher confirms. The event ID is derived from job, tenant and local date, so a retry or a second firing produces the same message and the consumers' inbox handles it once. | An outbox needs a tenant database. At-least-once delivery plus a deterministic ID gives the same guarantee. |
| 33 | Scheduler in `platform.yaml` (2.1) | Every runnable service is listed in `platform.yaml`. | The Scheduler, like the Gateway and the Migrator, is fixed platform infrastructure and is not listed. Its job store is a generated migration target (`scheduler` schema in the catalog database). | It has no module, audience, route or role. |
| 34 | Quartz schema (4.14) | Quartz.NET with a database job store. | The job-store tables come from Quartz's own create scripts (shipped inside the Quartz package), run by the Scheduler's migrations. Quartz never creates or alters tables itself at runtime, it only validates them. After a Quartz upgrade that changes the schema, add a migration that runs the script again (it only creates what is missing). | Keeps the Migrator the only thing that changes any schema, without copying Quartz's DDL into the repository. |
| 35 | Messaging and files in every host | Not specified. | `AddPlatform` (module hosts) registers messaging and file storage; the Gateway does not, and the Scheduler registers only messaging. Their settings (`RabbitMq:*`, `Storage:*`) are required only where used. | The Gateway neither publishes events nor stores files; requiring those settings there would be noise. |
| 36 | `AllInOne.Host` (2.2, 13) | One process with every module. | Its module references and registrations are generated from `platform.yaml`. It presents itself as the first service for service-to-service credentials, and calls between modules still use HTTP, to the process's own address (`ServiceClient:LocalAddress`). The AppHost runs it with `AppHost:Layout=all-in-one`; it is not part of the published compose file. | Calls through HTTP and tokens keep a module identical in both layouts, so there is one code path to test. Compose describes the production-like layout. |
| 37 | Emulator credentials (8) | No secrets in the repository. | The published compose file contains Azurite's well-known development account name and key. | They are public (Microsoft documents them), valid only against the emulator, and the compose file is for local runs. The secret scan allows exactly this value. |
| 38 | AppHost ports | Not specified. | The AppHost's OTLP and resource-service ports are 15101 to 15104, outside the range Aspire hands to services; the original 19100 to 22100 collided with a service's random port once. | Found while running the stack. |
| 39 | Tests for SignalR | Push is verified. | The test uses long polling against the in-memory server (WebSockets need a real socket). The Redis backplane across two instances is not tested. | The hub, groups and authorization are the same code on either transport. |
| 40 | TypeScript version (1) | Latest TypeScript. | TypeScript **6.0** (the latest 6.x), not 7. | `typescript-eslint` (needed for every lint rule) supports TypeScript below 6.1. Move to 7 when `typescript-eslint` does; the version is one line in the pnpm catalog. |
| 41 | Accessibility lint (6.6) | WCAG 2.2 AA with automated axe checks. | No `eslint-plugin-jsx-a11y`. The axe checks in Playwright cover the rendered pages, and MUI provides the semantics. | The plugin doesn't support ESLint 10 yet. Add it back when it does. |
| 42 | Package scope in the frontend (2.1) | Names come from `platform.yaml`. | `package.json` names (`@acme/web-core`, ...) and imports repeat the product name. | JavaScript package names can't be generated into every import. Renaming the product is the same one-time codemod as for C# namespaces (entry 4) (planned with `scripts/new-module` in milestone 6). |
| 43 | Tenant settings API (6.4, 7.3) | `useTenantSettings()` and `useFeature()` exist in `web-core`. | The frontend reads `GET /api/tenancy/v1/me/settings` (`{ branding, features, values }`) and treats a missing endpoint or an empty answer as the defaults. The endpoint itself is built with the customization ladder in milestone 5. | The contract is fixed now so milestone 5 only has to serve it; a tenant with no settings works today. |
| 44 | Custom fields API (7.3) | `GET /api/purchase-request/v1/custom-fields?entity=...` returns definitions. | `CustomFieldsSection` and the module use it as documented (an array of definitions); the endpoint is built in milestone 5. A missing endpoint shows no extra fields. | Same reason as entry 43. |
| 45 | Draft sharing (7.1, 7.4) | A feature flag turns "Share draft" on. | The flag shows a "Copy link to draft" button. Server-side sharing (who may open a draft) is added with the flag in milestone 5. | The prompt doesn't define what sharing does; the flag and its place in the UI are in. |
| 46 | End-to-end tests (6.6) | Playwright against the composed app. | In milestone 4 the Playwright tests run the **built** shell and module, served with the Gateway's CSP, with the API mocked in the browser. They cover composition, roles, error isolation, CSP, branding, CSRF and Idempotency headers, and axe. Tests against the real stack arrive with `dev-up` in milestone 5. | The composed stack needs the demo tenants (milestone 5). |
| 47 | Idempotency-Key (4.7, 6.4) | Sent on create requests. | `platformFetch` sends a fresh `Idempotency-Key` on every POST that doesn't carry one. | The client can't tell a create from an action; the server only enforces the key where an endpoint requires it. |
| 48 | Action names (7.3) | The frontend shows buttons from `allowedActions`. | The module lists the action names (`approve`, `reject`, ...) in one file, `actions.ts`, because the OpenAPI document types them as plain strings. | Making `allowedActions` an enum in the API would generate them; left as a follow-up to avoid changing the contract. |
| 49 | Module Federation | Remote name is the module key. | The container is assigned on the global object (`library.type: global`), because a key such as `purchase-request` isn't a valid variable name. Shared singletons also list the sub-paths `react/`, `react-dom/` and `@mui/material/`, so a module's deep imports use the shared copy. | Both needed for the build to work and for theming to reach modules. |
| 50 | Menu icons (6.2) | Manifest names an icon. | `ui-kit` ships a small, named set of icons; an unknown name shows a generic one. | Importing the whole icon library adds megabytes to every page. |
| 51 | Notification UI (6.1) | Not specified. | The shell has no notification bell yet. The Notification service (history, unread count, SignalR hub) is complete; the UI comes with the add-on work in milestone 5. | Keeps milestone 4 to the shell contract. |
| 52 | API numbers | Money and quantities are decimals. | The OpenAPI generator types them `number | string`; `toNumber()` in `web-core` normalises them. | ASP.NET Core's OpenAPI output allows both. |
| 53 | Where settings are declared (7.3) | `PurchaseRequestSettings` is the module's record. | Settings records and feature-flag keys live in `Contracts`, found by attribute, and modules read them through `ITenantSettings<T>`. | Tenancy edits them and the module reads them, and neither may reference the other. This also lets Tenancy validate a value (ranges, allowed strategy keys) without loading the module. |
| 54 | Strategy keys check (7.2) | `Migrator --catalog` validates all tenants' keys. | A key is validated when it is saved (`[AllowedValues]` on the setting). The Migrator does not re-check stored values. | An unknown key falls back to the default with a warning, as specified, so a stale value cannot break a tenant. |
| 55 | Flags and OpenFeature (7.3) | `IFeatureFlags` as an OpenFeature provider. | The catalog provider implements OpenFeature's `FeatureProvider` and `IFeatureFlags` calls it directly, instead of going through the SDK's process-wide `Api.Instance`. | The SDK's global provider would be shared by every host in a process (and by tests). A different provider can still replace it in DI. |
| 56 | Custom field values on the wire (7.3) | `"customFields": { "cost-center": "CC-100" }`. | Values are strings (a number field sends its digits as text). The server parses and validates them. | One JSON shape for every field type, and a stable OpenAPI schema. |
| 57 | Notification UI | See entry 51. | Still not in the shell. The Notification service is complete. | Left for a product decision on where the bell lives; nothing depends on it. |
| 58 | Local HTTPS trust (8) | A locally trusted certificate from mkcert. | `scripts/dev-up` creates the certificate with mkcert and asks to trust it (`mkcert -install`) only when a terminal is attached; otherwise it tells you to run it. The Playwright tests against the real stack ignore certificate errors. | Trusting a certificate authority changes the machine and needs a password, so it is never done silently. |
| 59 | Aspire certificate API | Not specified. | The AppHost uses Aspire's `WithHttpsCertificate`, which is marked experimental, to serve the Gateway with the mkcert certificate. | It is the supported way to replace the development certificate; the pragma is local to that line. |
| 60 | Sign-in pages and CSP | `form-action 'self'`. | On the sign-in host only, `form-action` also allows the tenants' hosts. | Browsers apply `form-action` to the redirect that follows a form post, and signing in ends with a redirect back to the tenant's host. Found by running the real stack in a browser. |
| 61 | License exceptions (1) | No library that needs a paid license unless recorded here. | Six NuGet packages are recorded in `docs/license-exceptions.json`: four are open-source licenses that the package declares as a file or a URL instead of an SPDX expression (Apache.Arrow, Fractions, Mono.Cecil, NetArchTest.Rules), and two are Microsoft's free-of-charge native libraries (SqlClient SNI, Identity.Client NativeInterop). | None needs payment. `scripts/check-licenses` fails on anything new until someone decides. |
| 62 | Actions pinned by SHA (9) | Supply-chain checks in CI. | Every action is pinned to a commit SHA (the tag is in a comment); Dependabot proposes updates. The Aspire CLI is installed as a .NET tool (`Aspire.Cli`) at the version of the AppHost SDK. | Tags can be moved; a SHA cannot. |
| 63 | Per-service CI tests (9) | Each workflow runs its service's tests. | Integration test classes carry `[Trait("service", "{key}")]`; a service workflow runs the classes of its service (plus the architecture tests and the drift check). `backend-core.yml` runs everything for changes to `Core`, `Contracts`, the tools and the test support. | There is one integration test project for the whole solution, so the trait is what ties a test to a service. |
| 64 | Images (9) | Multi-stage, digest-pinned, non-root, health check. | One parameterised Dockerfile for the services, one for the Gateway (which also carries the built frontend). The base images are pinned by the digest of the multi-architecture index. | Same patterns for every service, so one file to keep correct. |
| 65 | Adding a module changes the catalog | `scripts/new-module` needs no manual edit. | The catalog database seeds the list of modules and plans from `platform.yaml`, so adding a module also adds a catalog migration (named `Module{Name}`). `scripts/new-module` creates it for every provider; if you edit `platform.yaml` yourself, add it by hand. | Seed data is part of the EF Core model; `MigrationsConsistencyTests` (every context, both providers, no database needed) fails if a model change has no migration. |
| 66 | Dev-dependency advisories (9) | `pnpm audit` in CI. | `handlebars` (pulled in by `eslint-plugin-boundaries`) is forced to 4.7.10 or later with a pnpm override. One advisory is ignored, on `braces` (stack exhaustion on deeply nested glob patterns, no patched release), in the same lint-time chain, which only reads this repository's own patterns. | Nothing here is shipped; revisit when `braces` has a patched release or the plugin drops it. |
| 67 | Services call each other by name (compose, AppHost) | Service discovery resolves `http://{service-key}`. | The AppHost gives every service the addresses of the others (`WithReference`). Found by onboarding a tenant through the Tenancy service on the real stack, which calls Identity. | Without it a service could only call another through the Gateway. |
| 68 | Two database providers, every data test on both (4.13, 9) | Migrations and tests for SQL Server and PostgreSQL. | `platform.yaml` lists `sqlserver` only; the PostgreSQL migrations projects are not in the tree. The provider code, Quartz scripts and AppHost option stay, tests follow `PlatformInfo.DatabaseProviders`, and `scripts/add-postgresql` restores PostgreSQL (migrations from commit `17db99a`, a catch-up migration per context, consistency check). | Two migration sets and doubled test time without a PostgreSQL deployment. See ADR 0011's amendment. |
